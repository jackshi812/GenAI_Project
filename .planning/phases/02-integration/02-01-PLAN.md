<task owner="Ginger">
  <name>Task 1 — Implement the persistent MCP tool client</name>
  <files>graph/tools_mcp.py, graph/tools.py, graph/build.py</files>
  <action>
Create `MCPTools`, implementing the async interface from `graph/tools.py`.
Make it an async context manager that starts `python -m mcp_server.server` with
the MCP SDK's stdio client, creates one `ClientSession`, calls `initialize()`,
and keeps that session open for the complete graph run. Close it once when the
turn finishes.

`rag_search` and `web_search` call the literal MCP tool names, inspect returned
text content blocks, decode their JSON once, and pass the resulting values
through the same pydantic validation helper used by the fixture client. On a
call failure, raise `RuntimeError` with the tool name at this boundary; the Retriever
catches it, uses an empty result for that call, and returns a truthful error
`StepEvent`. It never produces invented evidence.

Update the private async runner in `graph/build.py` to select `FixtureTools` or
`MCPTools` from `TOOL_MODE=fixture|live`. Default to `live` for the final app.
The public `run_graph(transcript) -> AssistantResult` signature does not change.
One call to `run_graph` creates one MCP server/session, even though the Retriever
makes one private call and up to three live calls. This preserves one rate-limit
state for the full turn and avoids spawning several subprocesses. The server
closes after the turn, so its process-local TTL cache is not expected to survive
an app rerun; Austin proves the graded cache behavior by repeating a query in
`mcp_server/smoke.py` while one server session remains open.
  </action>
  <acceptance_criteria>
    - MCP discovery through this session returns exactly `rag.search` and `web.search`
    - One graph turn uses one server process and one initialized client session
    - MCP JSON content blocks validate into `RagResult` and `WebResult` objects
    - Austin's `mcp_server/smoke.py` records a cache hit for an identical query repeated within one session; integration makes no cross-turn cache-hit claim
    - An empty or failed live call preserves private results and records `status: error`; it does not crash or invent a match
  </acceptance_criteria>
</task>
