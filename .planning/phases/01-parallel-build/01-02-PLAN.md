**First, the stubs — twenty minutes of work that removes your only dependency on Austin.**

**Design the seam now, not on August 17.** The temptation is to write two quick functions returning raw lists and swap them for a real MCP client later. That swap is not a swap: a real MCP call is `async`, returns protocol content blocks rather than lists, needs the server subprocess started and torn down, and needs its JSON decoded and validated. Discovering that during integration week, with one day of slack behind it, is the most likely way this project fails. It costs about thirty extra minutes to prevent, and you are the only person who can prevent it.

So define one interface both implementations satisfy, in `graph/tools.py`, as a small `Protocol`:

```
async rag_search(query: str, **filters) -> list[RagResult]
async web_search(query: str, num: int = 10) -> list[WebResult]
```

The only accepted `rag_search` filter keys are `price_max`, `price_min`,
`category`, `brand`, and `k`; forward no other key.

The interface is async because the official MCP stdio client is async. Make `graph/tools_stub.py` implement the same async methods even though fixture reads are immediate, and make the graph nodes async. Do **not** call `asyncio.run` once per tool call: that would start a new MCP server for each product, discard the server-side cache, and turn one user turn into several subprocess lifecycles. The one synchronous-to-async boundary is `run_graph`, around the whole graph run.

Both functions return **validated pydantic models**, never raw dicts, and both route their output through one shared `_decode(payload) -> list[Model]` helper. The stub feeds it fixture dicts; the future MCP adapter feeds it `json.loads(content_block.text)`. Same validation, same failure mode, same call site.

Then write `graph/tools_stub.py` implementing that interface against `fixtures.json`: `rag_search` returns the `rag_results` list with `price_max` applied locally so the budget query visibly does something; `web_search` returns the `web_results` entry for the query, or an empty list on a miss. The class may use a no-op async context manager so it has the same lifecycle shape as the Phase 2 MCP client.

**Fixture lookup is exact-match on one shared key**, not "best match": take the first eight whitespace-delimited words, lowercase, collapse whitespace, and use the result as the dictionary key. Austin's replay and Jack's recording script use the same helper rule. A miss returns an empty list and logs a one-line warning. Fuzzy lookup produces silent wrong answers that look like working code.

Also handle the empty and error cases here rather than later: an empty result list must flow through the Retriever without raising, and a tool exception must become an empty list plus a `StepEvent` with `status: "error"`. The graph should degrade to private-only results rather than crash — that is also what saves the demo if Serper is down.

**Now the Retriever node (GRAPH-04), in `graph/retriever.py`.** This node is the project's core value and holds most of the ten Planning and Tool Use points. Take your time here.

Step one: when `use_private` is true, call
`await rag_search(state["semantic_query"], **state["filters"])`. The first
argument is never the raw transcript. Take the top three results as `RagResult`
objects. For this project, every ordinary shopping request uses private data;
`use_private` is false only on the explicit safety stop. In that case call no
tool, return no products, and record a skipped Retriever step.

Step two, only when `use_live` is True: build **one live query per product** from the matched catalog title, roughly three queries per turn (D-06). Truncate each title to its first eight words — full Amazon titles are marketing prose and match nothing in a shopping search. One query per category would be cheaper, but per-field provenance is only meaningful if the live price was fetched for that specific product. The bounded call volume makes Austin's rate limiter meaningful; his process-local TTL cache is a separate graded server behavior proved by repeating one query in the MCP smoke client.

Step three, the three-stage match (D-01). Neither title score nor derived brand works alone here: `sku` means nothing to the web, and `brand` is guessed from the title's first token. Similarity, mechanical variant guards, and selective LLM confirmation make the match defensible without paying for an LLM call on every product.
- Stage A, mechanical shortlist: normalize both titles by lowercasing, stripping punctuation, and dropping only this fixed filler set: `the`, `a`, `an`, `for`, `with`, `and`, `of`, `by`. Do not drop numbers, units, model strings, or colors. Then score with `difflib.SequenceMatcher(None, a, b).ratio()`. Keep the top two or three candidates and inspect the best score.
- Stage B, apply deterministic variant guards before score thresholds. Extract explicit pack/count/piece tokens, size-and-unit tokens such as `12 oz`, model-number tokens, and common color tokens from both titles. If both titles state a value and the values disagree, reject the match. If only one title exposes a variant token, force the pair into the ambiguous path even when its similarity exceeds `0.60`; missing variant evidence is not proof of equality.
- Stage C, confirm only ambiguous matches. A best score below `0.35` is automatically rejected with verdict `different`; a best score above `0.60` is automatically accepted with verdict `same` only after the variant guards pass; all other cases call `load_prompt("match_confirm")` with the shortlisted candidates. The LLM returns the chosen candidate index (or none), verdict, and one-sentence reason. This preserves a `MatchInfo` for every product without paying for three LLM calls on an ordinary turn. Store an explicit reason such as `auto-accepted above 0.60 with matching variant tokens` or `auto-rejected: 2-pack vs 4-pack`. Jack exposes these details in a collapsed expander (D-14).

Write `prompts/match_confirm.md` with the "consumed by" comment on line one. The prompt must tell the model that different pack sizes, different piece counts, and different colorways are **different products**, and that when unsure it should say `unsure` rather than force a match. A wrong match produces a fabricated price conflict, which is worse than no match at all.

Step four, reconciliation (D-02). **`conflicts` means genuine disagreement only — in practice, price.** Build a `Conflict` when both sides carry a number and they differ by more than 10% or more than $2, whichever is larger, recording the 2020 value, the live value, and the direction.

**Do not put `rating` or `availability` in `conflicts`.** They are live-only fields, not disagreements: the catalog has no rating in any row, so there is nothing for the live rating to disagree *with*. Putting them in the conflicts list makes Jack render a perfectly good live rating in red with a warning symbol, which tells a grader the system found a problem where none exists.

Per-field provenance is carried by the **structure**, not by the conflicts list. `private` holds what the 2020 catalog knows (price, no rating). `live` holds what the web knows (price, rating, availability). A field present on one side and absent on the other is self-evidently single-sourced, and Jack labels the two columns accordingly.
