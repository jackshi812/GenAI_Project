  <action>
Create `catalog/search.py` with a single public function:

`search(query, price_max=None, price_min=None, category=None, brand=None, k=5) -> list[dict]`

The query string goes to Chroma's `query_texts`. **The numeric constraints never touch it** — they become `where` clauses (RAG-04).

Build the where clause as a list of conditions, then assemble it by length:
- `price_max` adds a `$lte` condition on `price_low`
- `price_min` adds a `$gte` condition on `price_low`
- `category` adds an `$eq` condition on `category`
- `brand` adds an `$eq` condition on `brand`

**Chroma rejects `$and` with a single element in several versions.** So: zero conditions means pass `where=None`; exactly one condition means pass that condition dict directly; two or more means wrap them in `{"$and": [...]}`. Getting this wrong produces a confusing validation error on the simplest possible query.

**Filter on `price_low`, not `price_high`.** A product listed at `$15.99 - $44.99` qualifies for "under twenty dollars" because a variant genuinely costs $15.99, and the UI will show the full range. One rule, applied consistently, and defensible on camera.

Return a list of dicts, each carrying the seven keys spec lines 99–107 mandate — `sku`, `title`, `price`, `rating`, `brand`, `ingredients`, `doc_id` — plus the additive keys Jack's UI needs: `image_url`, `product_url`, `category`, `price_low`, `price_high`, `similarity`.

Three field rules that are easy to get wrong:
- `price` is `price_low` when parsing succeeded, otherwise the raw string. The spec types it "number or string", so this satisfies the schema literally while keeping honest data for the unparseable rows.
- `rating` is always `None`. The dataset has none. The key must exist because the spec's schema lists it; the value must be null because inventing one would be fraud and is trivially detectable.
- `ingredients` is always `None`. The column is empty in every row and the spec marks the field optional.

Compute `similarity` as `1 - distance` from Chroma's cosine distance, so a higher number reads as a better match. Ginger displays this on screen as match confidence (D-14).

Create `mcp_server/server.py` — one MCP server, over stdio, exposing exactly two tools (MCP-01).

**Use the low-level `mcp.server.Server` class with explicit `@server.list_tools()` and `@server.call_tool()` handlers, not `FastMCP`.** Two reasons, both concrete. First, MCP-02 is graded on discovery returning tool names with their JSON schemas, and hand-writing the `inputSchema` dicts makes that visible in your code and in the grader's terminal. Second, `FastMCP` derives tool names from Python function names, and `rag.search` contains a dot, which is not a legal Python identifier. Fighting that is more work than writing two handlers.

`list_tools` returns exactly two `Tool` objects, named literally `rag.search` and `web.search`. The spec names them with dots, so keep the dots. Each carries a description and an `inputSchema` that is a real JSON Schema object with `type`, `properties`, and `required`.

`rag.search` input schema: required `query` (string); optional `price_max` (number), `price_min` (number), `category` (string), `brand` (string), `k` (integer, default 5). Its description should say it searches the private Amazon 2020 catalog and note that the corpus contains no ratings.

`web.search` input schema: required `query` (string); optional `num` (integer, default 10). Task 6 implements it.

`call_tool` dispatches on the tool name. For `rag.search`, call `catalog.search.search` with the arguments and return the results as a single JSON text content block. Both folders are yours, so importing `catalog` from `mcp_server` is fine — do not build an adapter layer between them.

Transport is stdio via `mcp.server.stdio.stdio_server()` inside an asyncio entry point. **Nothing may print to stdout.** stdout is the MCP wire protocol; a stray `print()` corrupts every message after it. All diagnostics go to stderr or to the log file.

Implement request logging here so both tools inherit it (MCP-07). Write one JSON object per line to `mcp_server/logs/mcp.jsonl`, appending. Per call, log two lines: a request line with an ISO-8601 UTC timestamp, direction `request`, the tool name, and the arguments; and a response line with a timestamp, direction `response`, the tool name, the elapsed milliseconds, the result count, and — for `web.search` — the list of source URLs returned (spec line 114 asks for the source URL where applicable).

**Never log a secret.** Before writing an arguments dict, drop any key whose lowercase name contains `key`, `token`, or `secret`, and never log the contents of an environment variable. Nothing in either tool's arguments should ever be a credential, and this filter is the cheap insurance that keeps it that way.

Create `mcp_server/logs/` and remind Jack that `.gitignore` needs a `mcp_server/logs/` line — you do not edit `.gitignore` yourself, he owns it.
